# n8n workflows

n8n is the orchestrator when `NEXUSFLOW_N8N__ORCHESTRATION=n8n`. It decides
*when* the next step runs; the platform decides *what* is allowed. Every
workflow calls only the internal automation API, with a service token, and
those endpoints return identifiers and counters, never tenant data. The one
exception is workflow 5, which may also ask n8n's own API (on loopback) to
retry a failed execution.

The JSON files are generated by `scripts/generate_n8n_workflows.py` (the
source of truth; a unit test fails if the committed files drift from it) and
linted by `scripts/validate_n8n_workflows.py` in CI.

| File | Trigger | Calls | Service-token scopes |
|---|---|---|---|
| `01-data-collection.json` | every minute | `POST /dispatch`: starts due scheduled workflows, at most once per schedule slot | `automation:collect` |
| `02-change-detection.json` | event `collection.completed`; every 5 min | `POST /detect`, `POST .../workflow-runs/{id}/advance` (finishes the run), `POST /detect/sweep` (safety net) | `automation:detect`, `automation:collect` |
| `03-ai-analysis.json` | event `changes.detected` | `POST /analyze` when the workflow opted into analysis | `automation:analyze` |
| `04-alerting.json` | event `changes.detected` | `POST /alerts/evaluate` | `automation:alert` |
| `05-failure-recovery.json` | n8n error trigger; event `job.failed` | `POST /failures`, n8n's `POST /api/v1/executions/{id}/retry`, `POST /operator-alerts` | `automation:recover`, `automation:operator_alert` |

Alerts on failed runs and on AI insights are always evaluated by the platform
itself; they do not depend on n8n.

## Failure recovery (workflow 5)

When a workflow execution fails, n8n's error trigger starts workflow 5:

1. **Record failure** - `POST /failures` with the failed execution's id and
   `retry_of` (the execution it retried, if any). The platform counts failures
   per *retry chain* itself (Redis, idempotent per execution id), so a replayed
   or forged request cannot reset the count. It answers either
   `{"retry": true, "delay_seconds": N}` - exponential backoff from 30 s, capped
   at 15 min, for at most 3 retries of idempotent steps and only while the
   tenant's automation is not frozen - or `{"retry": false}` after recording a
   dead letter.
2. **Exponential backoff** - a *Wait* node sleeps `delay_seconds`.
3. **Retry the execution** - `POST http://127.0.0.1:5678/api/v1/executions/{id}/retry`
   on n8n's own API, authenticated by the `NexusFlow n8n API key` credential.
   The validator allows this call only to that exact loopback URL, only with
   that credential, and the id is reduced to `[A-Za-z0-9_-]` first.
4. When no retry is allowed: **Page operators** - `POST /operator-alerts`,
   which the platform de-duplicates (identical pages go out once per 15 minutes).

Platform jobs that exhaust their retries arrive as `job.failed` events and are
paged the same way (their dead letters already exist).

## Security model

* **One token per workflow.** A leaked token grants one workflow's scopes only.
  Revoking it disables exactly that workflow:
  `nexusflow service-account disable --workflow-key <key> --reason ...`.
* **Signed events.** The platform POSTs events to n8n's internal webhook URLs
  with an HS256 JWT that lives 60 seconds. Every webhook node uses
  *JWT Auth*, so forged or stale calls are rejected. Receivers are idempotent,
  so a replay within the validity window has no effect.
* **No code, no egress.** The validator rejects node types that execute code or
  commands; HTTP calls to anything but `http://api-internal:8001/internal/v1/`
  (plus the one n8n retry URL above); redirects; inline auth headers; webhooks
  without JWT; *Wait* nodes that resume on anything but a time interval;
  embedded secrets; stored success-execution data; and workflows without a
  timeout or error workflow.
* **Kill switches.** One workflow: disable its service account. Everything:
  `nexusflow kill-switch engage --reason ... --deactivate-n8n <ids>`, which
  refuses automation calls platform-wide (even from tokens that still work)
  and unpublishes the given n8n workflows. See docs/INCIDENT_RESPONSE.md.

## Installation

1. Issue one service account per workflow and keep the printed tokens (each
   is shown once):

   ```bash
   nexusflow service-account create --name n8n-collection --workflow-key data-collection --scope automation:collect
   nexusflow service-account create --name n8n-detection --workflow-key change-detection --scope automation:detect --scope automation:collect
   nexusflow service-account create --name n8n-analysis --workflow-key ai-analysis --scope automation:analyze
   nexusflow service-account create --name n8n-alerting --workflow-key alerting --scope automation:alert
   nexusflow service-account create --name n8n-recovery --workflow-key failure-recovery --scope automation:recover --scope automation:operator_alert
   ```

   In the Compose stack, run them in the internal API container:
   `docker compose run --rm api-internal nexusflow service-account create ...`.

2. In n8n, create an API key (*Settings > n8n API*). Put it in
   `./secrets/n8n_api_key` (the platform uses it to unpublish workflows during
   an incident; restart `api-internal` afterwards).
3. In n8n, create these credentials. The names must match exactly, because
   the workflows reference them by name.
   * *Header Auth* credentials named `NexusFlow token - data collection`,
     `NexusFlow token - change detection`, `NexusFlow token - ai analysis`,
     `NexusFlow token - alerting`, `NexusFlow token - failure recovery`.
     Set the header name to `Authorization` and the value to `Bearer <token>`.
   * A *Header Auth* credential named `NexusFlow n8n API key`: header name
     `X-N8N-API-KEY`, value the n8n API key from step 2. Only workflow 5 uses it.
   * One *JWT Auth* credential named `NexusFlow events JWT`: passphrase,
     algorithm `HS256`, and the same secret as `NEXUSFLOW_N8N__WEBHOOK_JWT_SECRET`
     (`./secrets/n8n_webhook_jwt_secret`).
4. Import `05-failure-recovery.json` first and note its workflow ID. In the
   other four files, replace `REPLACE_WITH_FAILURE_RECOVERY_WORKFLOW_ID` with
   that ID, then import them.
5. Publish the five workflows (n8n 2.x replaced "activate" with "publish"), then
   set `NEXUSFLOW_ORCHESTRATION=n8n` in `.env` and recreate the platform
   containers. Until then the platform orchestrates itself (`internal`).

## n8n hardening (set in `docker-compose.yml`)

`N8N_BLOCK_ENV_ACCESS_IN_NODE=true`, `NODES_EXCLUDE` for code, command, SSH,
FTP and file nodes, `N8N_DIAGNOSTICS_ENABLED=false`, `N8N_TEMPLATES_ENABLED=false`,
`N8N_VERSION_NOTIFICATIONS_ENABLED=false`, `N8N_SECURE_COOKIE=true`,
execution-data pruning, a dedicated PostgreSQL database and role, an
`N8N_ENCRYPTION_KEY` from a secret file, and no route from the public reverse
proxy (the editor is reached through an SSH tunnel or VPN only). The image tag
is pinned (`N8N_VERSION`); n8n ships security fixes often, so keep it current.
